# MongoDB 故障恢复验收

## 自动化覆盖与限制

`make test-mongodb` 在真实数据库上验证消息、序号、Outbox 原子提交与回滚、v2 → v3 升级、结构漂移拒绝，以及事务故障注入与幂等恢复。

`MongoTransactionFailoverTest` 使用应用自有异常和会话装饰器注入错误。提交确认丢失用例先真实提交，再隐藏确认，最终使用相同 `client_message_id` 恢复。此套件没有关闭 Primary 或制造网络分区，不代表完成真实选主验收。

## 专用三节点环境验收（待执行）

使用独立的 `test_*` 数据库、三个有投票权的数据节点及多数派写入，准备好业务 RPC、服务账号、可收集的客户端结果和数据库快照。禁止在生产集群运行故障注入。

1. 记录无故障基线；并发发送固定会话与多会话消息，保存发送者、原始载荷及客户端幂等键。
2. 在持续写入与提交过程中，对当前 Primary 执行受控 step-down；另一次独立实验停止 Primary，确认其余节点实际选出不同的 Primary。记录故障与选举时间，不用应用自有异常代替真实故障。
3. 对失败或结果未知的请求，在新 Primary 就绪后以原载荷、原幂等键重试；同一幂等键载荷改变时必须拒绝。
4. 汇总成功返回的消息与最终持久化结果：每个发送者/客户端幂等键最多一条消息；会话序号不重复；每条消息对应一个 Outbox 事件，事件的消息 ID、会话和序号完全一致。
5. 专门核对提交中的未知请求最终能否恢复，分别报告可恢复、明确失败、仍未知的数量。恢复节点并确认复制追平后，再核对一遍数据。
6. 在隔离环境单独验证网络分区；记录分区方式、持续时间及客户端可达节点，不能把单纯超时与真实分区混为一谈。

## 容量与预算记录（待采集）

保留默认 600ms 消息预算与 150ms 提交上限，分别记录基线、网络延迟扰动、选主期间及恢复后的数据：

| 指标 | 统计方式 |
| --- | --- |
| 提交 P95/P99 | 每次 commit 调用单独计时，区分成功、失败、重试 |
| 整笔事务重试 | 按请求统计 TransientTransactionError 后的重放次数 |
| 提交结果未知比例 | 结果未知请求数 / 总发送请求数 |
| 最终恢复成功率 | 通过原幂等键确认持久化的未知请求数 / 未知请求数 |
| RPC 超时与排队 | 分别记录 SendMessage、MarkRead 的延迟、超时率与 worker 使用率 |

请求总耗时与单次提交耗时必须分开报告。采用实际部署的节点配置和网络环境，在预先约定的吞吐与可用性目标下决定预算是否需要调整；不能仅凭本地单节点测试结果提高或降低默认值。

此文档描述待执行的验收方法，不是三节点选主、网络分区或生产容量测试的通过证明。
