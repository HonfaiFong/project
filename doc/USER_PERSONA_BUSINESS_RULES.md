# 真身与匿名分身业务规则

更新日期：2026-10-11。

本文整理用户在本次讨论中给出的产品目标和最终业务规则，作为后续开发与验收依据。产品参考“一罐”的匿名互动理念，但本文不声明复现该产品当前版本的全部行为。

身份相关规则以本文为准：早期“一个真身 + 最多四个固定分身”的方案已被替代。迁移、协议兼容与部署细节见 [Persona 迁移说明](PERSONA_IDENTITY_MIGRATION.md)；项目总体技术背景见 [后端构建总规范](SOCIAL_APP_BACKEND_BUILD_SPEC.md)。

## 1. 账号与社交身份

| 概念 | 职责 | 对外表现 |
| --- | --- | --- |
| User | 登录账号、认证、安全、风控、封禁与行为归属 | 账号与分身的关联仅在内部使用 |
| MAIN（真身） | 长期、稳定的公开主身份 | 有公开主页，可展示真身发布的内容 |
| ALIAS（分身） | 账号拥有的内部匿名能力 | 按内容或会话展示匿名形象，不提供可追踪的公开小号 |

真身是稳定的公开主身份，不等同于手机号认证或身份证实名认证。以后接入实名验证时，实名材料仍属于私密账号信息，不存入公开 Persona 资料。

UserService 统一管理 User 与 Persona；AuthService 管理登录与认证。身份模式不要求拆成两个微服务。

## 2. 身份生命周期

1. 新注册账号在同一个事务中创建 User、唯一 MAIN、唯一内部 ALIAS 和对应 Outbox 事件；任一步失败则整体回滚。
2. 每个账号恰好有一个真身。真身不能通过普通接口额外创建、单独删除，或转换为分身。
3. 分身是匿名模式，不开放创建多个固定分身、经营独立公开资料页的产品功能。内部 ALIAS 由服务端维护，不由客户端选择其数据库 ID 或修改其资料。
4. 旧账号首次使用匿名能力时，由服务端受控补建内部 ALIAS。并发请求必须复用同一个内部身份。
5. 已有内部 ALIAS 被停用或删除时，拒绝匿名行为；不能通过重复创建、自动复活来绕过停用。
6. 历史固定分身及其 ID 保留用于内容归属、历史记录和审核；不能自动合并、重分配历史内容，也不能继续用于新的匿名操作。

账号注销、历史信息匿名化及保留期限需要单独制定产品规则。已有内容或会话时，不能直接物理删除身份行而使历史归属丢失。

## 3. 操作权限

| 操作 | MAIN | ALIAS | 补充规则 |
| --- | --- | --- | --- |
| 发帖 / 发布罐头 | 允许 | 允许 | 发布时选择身份，匿名昵称按本次发布保存 |
| 评论 / 回复 | 允许 | 允许 | 匿名展示限定在所在帖子或讨论范围 |
| 创建私聊 | 允许 | 允许 | 建立会话时固定参与身份 |
| 发送私聊消息 | 允许 | 允许 | 使用已有会话成员身份，不能逐条切换模式 |
| 点赞 / 取消点赞 | 允许 | 禁止 | 使用真身，反作弊按账号执行 |
| 关注 / 取消关注 | 允许 | 禁止 | 关注对象是公开 MAIN |
| 拉黑 / 取消拉黑 | 允许 | 禁止 | 效果按账号执行，覆盖双方全部身份 |
| 举报 | 允许 | 禁止 | 被举报对象可为匿名内容或会话行为 |
| 查看、修改自己的公开身份资料 | 允许 | 禁止 | 匿名昵称不是可编辑的固定分身资料 |
| 建立通用 WebSocket 连接 | 允许 | 禁止 | 连接使用账号 / MAIN 上下文 |

其他需要社交身份的操作默认使用 MAIN。新操作必须明确加入权限规则后才能开放；未指定、未知或不支持的操作一律拒绝。

“只能以 MAIN 行动”不影响账号管理自己的匿名内容：删除本人匿名帖子时，服务端按 User 归属判断权限，不要求当前 MAIN ID 等于匿名内容作者 ID。

## 4. 身份选择与授权

JWT 绑定 User，证明账号登录状态。发帖、评论及创建私聊时选择 MAIN / ALIAS，不因切换模式而重新登录或重新签发 JWT。

服务端从认证结果取得可信 User ID，并结合操作类型解析身份。客户端提交的 `user_id`、Persona ID 或匿名标识不能成为可信归属证明。旧接口携带 Persona ID 时，也必须校验归属、身份类型与状态。

每次关键行为检查：

- 账号存在、未删除且处于可用状态。
- Persona 属于该账号、未删除且处于可用状态。
- ALIAS 是服务端维护的内部匿名身份。
- 当前身份模式允许执行该操作。
- 具体业务允许执行该行为，包括拉黑、内容权限、会话成员资格及风控限制。

身份归属检查不能替代发帖、私聊等业务授权。用户切换身份时通过一次校验，也不能使后续行为永久免检。

MVP 可由客户端保存当前选择；不把全局 `current_persona_id` 存入 User。同一账号的不同设备可以有不同选择，多设备偏好同步留待后续需求。

## 5. 匿名昵称与内容展示

发帖、评论或创建匿名私聊时，可以填写本次使用的昵称；下一次独立操作可以使用不同昵称。服务端校验昵称后保存不可变展示快照，默认使用系统匿名头像。

同一个已建立的会话保持创建时的身份与昵称。编辑 MAIN 资料或下一次使用其他匿名昵称，均不能改写历史匿名内容及已有会话的展示信息。

真身内容可以出现在真身公开主页。匿名内容不出现在真身公开主页，也不能通过头像或昵称跳转到固定 ALIAS 主页。

本人可查看匿名内容管理视图；该视图需要账号认证，不对其他用户开放。它不等同于可被搜索、关注或浏览的分身主页。

对外作者形态示例：

```json
{
  "post_id": "30001",
  "author": {
    "identity_mode": "alias",
    "display_name": "一颗橘子",
    "avatar_key": "system:anonymous",
    "anonymous_ref": "opaque-post-scoped-id",
    "profile_accessible": false
  }
}
```

示例中的 `anonymous_ref` 由服务端生成，客户端不能指定。公开 ALIAS 作者没有固定 `persona_id` 或 `user_id`。

## 6. 匿名标识与隐私边界

匿名标识必须是不透明、不能反推出账号的值，并绑定明确的帖子、讨论或会话范围。同一身份在同一范围内可保持稳定，不同独立范围不能复用同一个公开标识。

例如，同一账号匿名发布帖子 P1 和 P2，两篇帖子的作者标识不同；P1 的作者与评论是否保持同一个讨论范围，应使用明确一致的范围规则。匿名私聊使用自己的会话范围，不能直接复用来源帖子的作者标识作为会话作者标识。

公开接口不得泄漏内部关联，包括：

- User ID、内部 ALIAS ID、账号与多个身份的映射。
- 可跨独立内容复用的匿名作者标识。
- 通过帖子、评论、Feed、随机罐头、搜索、关注列表或消息成员嵌套返回的内部身份字段。
- 可据以反查匿名身份归属的头像地址、个人主页入口或成员资料。

公开内容、会话和消息使用独立的公开响应结构。移除最外层字段还不够，嵌套对象也必须遵守同样规则。

内部数据库保留真实 User / Persona 归属，供删除本人内容、举报处理、封禁及反作弊使用。内部审核可追溯账号，不代表普通用户可查询这些关联。

历史记录缺少可靠模式或展示快照时，默认展示为不可关联的匿名作者。不能根据当前 Persona 资料补成 MAIN，或自动公开历史匿名关系。

## 7. 私聊与实时连接

建立私聊时固定双方展示身份和昵称快照，后续消息从会话成员快照取得作者身份。客户端发送消息只提供会话和消息内容，不能重新提交身份模式来更换发言者。

匿名会话中不能未经处理突然显示真身。另一种身份组合需要独立的受控会话建立流程，仍执行账号级拉黑和风险限制。

私聊目标只能是公开 MAIN，或具体来源内容及其范围内匿名标识。服务端解析匿名目标后再进行授权；不能要求客户端取得对方 User ID 或内部 ALIAS ID。

通用 WebSocket 连接使用账号 / MAIN 上下文。匿名发言身份由会话业务决定，不能直接把连接的 MAIN 写成匿名消息作者。Ticket 绑定身份不可变，旧连接不能由客户端任意改成另一身份。

## 8. 封禁、拉黑与反作弊

| 治理行为 | 执行依据 | 效果 |
| --- | --- | --- |
| 账号封禁 | User | 真身及匿名能力均不可继续行动 |
| 匿名身份停用 / 封禁 | 内部 ALIAS | 拒绝该匿名能力，禁止重建绕过 |
| 拉黑 | 双方 User | 覆盖双方所有身份的相关互动 |
| 举报审核 | 内容 / 会话 + 内部归属 | 可追溯账号，不向举报人公开身份映射 |
| 点赞、关注防刷 | User | 不因切换身份重复计数或绕过限制 |

例如，A 有真身 A1 和匿名能力 A2，B 有真身 B1 和匿名能力 B2。A 拉黑 B 后，B1/B2 与 A1/A2 的相关互动都应受限制；响应不能告知 A 哪些匿名内容或身份属于 B。

“相关互动”的具体范围以及已有会话的展示、历史消息是否可读，需在对应业务设计中明确；不能把未确定细节当成已实现行为。

## 9. 账号注册边界

账号注册、手机号绑定、QQ / 微信登录归并属于 Auth / User 账号层，不属于 Persona 匿名模型。当前第三方首次登录自动注册的流程，不意味着真身已通过手机号或实名验证。

若以后要求第三方首次授权必须绑定手机号，应调整认证和账号归并流程，不把该要求塞入 Persona 类型或匿名展示规则。

## 10. 后续功能与未确定事项

- 主动把历史匿名内容改为真身展示：留作后续功能，必须由用户明确确认公开，不能随资料修改、迁移或身份切换自动发生。
- 独立隐私设置、资料审核、多设备身份偏好同步：按实际需求另行设计。
- 同一帖子中多次匿名发言是否允许更换昵称、昵称唯一性或敏感词规则：需要具体内容产品规则，本文件仅确定保存每次写入的快照。
- 会话组合的复用、重复创建以及群聊身份规则：需要后续会话设计；本文件明确的是私聊身份固定和账号级授权。
- 注销、历史数据保留与匿名化期限：需要独立生命周期规则。

## 11. 验收场景

1. 新注册账号只有一个 MAIN 和一个内部 ALIAS，注册失败不留下半完成身份或事件。
2. 普通用户不能再创建第二个 MAIN 或多个固定 ALIAS，不能编辑内部 ALIAS 资料。
3. ALIAS 可发帖、评论和私聊；点赞、关注、拉黑、举报及通用连接使用 MAIN。
4. 其他账号的 Persona、封禁账号、停用或已删除身份不能通过行为授权。
5. 无效操作不会顺带创建匿名身份；已删除的内部 ALIAS 不被自动重建。
6. 匿名帖子不出现在真身主页，公开接口和嵌套对象不能返回账号关联。
7. 同一账号在不同帖子 / 会话的匿名标识不同，错误范围的快照不输出可关联标识。
8. 资料编辑不改变历史匿名昵称；缺少可靠历史快照时保持匿名。
9. 已有匿名会话不能通过单条消息切换为 MAIN；非成员不能借匿名标识进入会话。
10. 拉黑和账号封禁覆盖所有身份；本人仍可按账号归属管理自己的匿名内容。

## 12. 当前实现范围

本轮已落实 User / Gateway 身份规则、匿名快照与投影基础、公开协议结构及数据库迁移定义。Content、Social、Chat、Message 等服务的实际业务处理仍为骨架，上述业务规则是后续实施目标，不代表端到端功能已全部完成。

迁移尚需在真实 MySQL 环境验证。测试结果、升级顺序、破坏性协议更新与回滚限制详见 [迁移说明](PERSONA_IDENTITY_MIGRATION.md)。
